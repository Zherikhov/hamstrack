## About the project

Hamstrack is a **source-available** task tracker inspired by Jira, licensed under the **Elastic License 2.0** (ELv2, since commit 880c5cd — see `docs/adr/0010-elastic-license-2.md`). It is *not* open source under the OSI definition: ELv2 forbids providing the product as a managed service and forbids removing the licensing/authentication layer. Do not write "open source" about Hamstrack in code, docs, tickets or UI copy — that claim is the subject of HD-194. It must also not copy Jira's implementation, UI, naming, or proprietary behavior.

It must support two deployment models from the same core codebase:
- self-hosted installation (DC)
- hosted Cloud version

Performance, maintainability, and simple deployment are core requirements. When proposing architecture, libraries, or infra (auth, storage, multi-tenancy, billing, etc.), favor options that work in both deployment models — avoid baking in cloud-only assumptions without an equivalent self-hosted path.

**Current state:** Phase 4A complete (full-stack app running; React SPA ships as a single JAR via Maven). Stack: Spring Boot 4.1.0 / Java 21, Spring Web MVC, Spring Data JPA, Spring Security, PostgreSQL, Flyway, Lombok, jjwt. Frontend (`src/main/frontend/`): React 19, TypeScript, Vite 6, Tailwind v4, React Router v7, TanStack Query v5, Zustand v5, lucide-react. Full feature changelog, subsystem internals (admin/taxonomy, custom fields, user accounts, rate limiting, demo data, schema squash), the API surface map, and CI/CD are in **`docs/project-state.md`**. Roadmap & stack decisions: `PLAN.md`.

## DC vs Cloud (single codebase)

Hamstrack ships as one codebase in two modes, controlled by Spring profile `dc` or `cloud` (`SPRING_PROFILES_ACTIVE=cloud`). Differences between modes must be config/profile-gated behavior, never forked code.

The highest-severity bug class here is a query/service that forgets to scope by `workspace_id`/membership — in Cloud that leaks one tenant's data to another. Always resolve resources through workspace membership checks; return 404 whether the workspace doesn't exist or the caller isn't a member — never reveal existence via a 403.

**File storage** (`common.storage.FileStorage`): backend selected by `app.storage.type` (`local` | `s3`), profile defaults — `dc` → local FS (`app.storage.local.base-dir`, default `./data/attachments`, gitignored), `cloud` → S3 (`app.storage.s3.*`: bucket, region, optional `endpoint` + `path-style-access` for MinIO/S3-compatible stores, optional static keys — empty falls back to the AWS SDK default credentials chain). Implementations are `@ConditionalOnProperty`-gated beans (`LocalFileStorage` / `S3FileStorage`); inject the `FileStorage` interface, never a concrete class. Storage keys are server-generated (`ws/{wsId}/issues/{issueId}/{uuid}`) — original filenames live only in the DB. Upload size limit via `spring.servlet.multipart.max-file-size` (env `ATTACHMENT_MAX_FILE_SIZE`, default 25MB).

## Architecture

Package-by-feature under `com.hamstrack`, one top-level package per business area — `auth`, `workspace`, `project`, `issue` — plus `common` for cross-cutting infrastructure. Each feature package nests layer subpackages: `entity`, `repository`, `service`, `controller`, `dto`, `exception` (not every feature has all six).

- `common.entity` — `BaseEntity`/`CreatedOnlyEntity` mapped superclasses for `id`/`createdAt`/`updatedAt`. Use Spring Data JPA auditing (`@CreatedDate`/`@LastModifiedDate` + `@EntityListeners(AuditingEntityListener.class)`); `@EnableJpaAuditing` is on `HamstrackApplication`.
- `common.exception` — `AppException` (each subclass carries an `HttpStatus`), `GlobalExceptionHandler`.
- `common.security` — `JwtService`, `JwtAuthenticationFilter`, `SecurityConfig`.
- `common.config` — `@ConfigurationProperties` classes.

Schema managed entirely by Flyway; `spring.jpa.hibernate.ddl-auto=validate` only. `spring.jpa.open-in-view=false` — service methods touching lazy associations need `@Transactional`.

**IDs:** UUID v7 everywhere, generated by the application via `@UuidGenerator(style = UuidGenerator.Style.TIME)` (Hibernate 6/7). Never use `@GeneratedValue(strategy = IDENTITY)` or BIGSERIAL.

**Timestamps:** Use Spring Data JPA `@CreatedDate`/`@LastModifiedDate` (NOT Hibernate `@CreationTimestamp`/`@UpdateTimestamp`). In Hibernate 7, `@CreationTimestamp` does not set the value until flush, so values are null after `save()`. With `@CreatedDate` + `@EnableJpaAuditing`, Spring sets values during `@PrePersist`/`@PreUpdate` — immediately available after `save()`. The schema also has `DEFAULT NOW()` + DB triggers as a safety net for raw SQL writes outside JPA.

**PostgreSQL ENUMs:** Do NOT use `CREATE TYPE ... AS ENUM`. Hibernate 7 + PostgreSQL ENUM types cause JDBC type cast errors on INSERT (`column is of type X but expression is of type character varying`). Use `VARCHAR(N)` columns instead — enum values are validated at the application layer by Java enums.

**Jackson:** Spring Boot 4 does not include Jackson in `spring-boot-starter-web` by default. Add `jackson-databind` explicitly to `pom.xml`. **Jackson 2 vs 3 split:** Spring MVC now (de)serializes with Jackson 3 (`tools.jackson.*`), but Hibernate's JSON mapper and all our JSONB-backed fields use Jackson 2's `com.fasterxml.jackson.databind.JsonNode`. Jackson 3 has no built-in support for a Jackson 2 tree node, so any request/response carrying one (custom field values, field-def `config`) fails: read → `InvalidDefinitionException: Cannot construct instance of JsonNode (no Creators)` (HTTP 500/400), write → getter-noise dump `{"array":false,...}`. Bridged by `common.json.Jackson2NodeModule` — a Jackson 3 `JacksonModule` bean (auto-registered by Boot 4's `JacksonAutoConfiguration`, which collects all `tools.jackson.databind.JacksonModule` beans into the MVC `JsonMapper`) that round-trips Jackson 2 nodes via raw JSON. Keep entity/DTO JSONB fields on Jackson 2 `JsonNode` (Hibernate reads/writes those); the module handles the web boundary. Don't mix in `tools.jackson` node types on entities without also switching Hibernate's format mapper.

## Gotchas — don't re-debug these

- **`createdAt`/`updatedAt` null after `save()` with `@CreationTimestamp`**: In Hibernate 7, `@CreationTimestamp` sets values at flush time, not at `persist()`. Fix: use Spring Data JPA `@CreatedDate`/`@LastModifiedDate` + `@EntityListeners(AuditingEntityListener.class)` + `@EnableJpaAuditing` — these fire during `@PrePersist`/`@PreUpdate` and values are immediately available after `save()`.
- **Custom `@Component` Filter silently not authenticating**: Spring Boot auto-registers any `Filter` bean as a generic servlet filter *in addition to* `addFilterBefore`. Fix: `FilterRegistrationBean<YourFilter>` with `setEnabled(false)`.
- **404 on unmapped endpoint shows as 403**: container dispatches to `/error` which re-enters Spring Security unauthenticated. Fix: `.dispatcherTypeMatchers(DispatcherType.ERROR).permitAll()` in `SecurityConfig`.
- **"Access Denied … response is already committed" ERROR when an SSE emitter times out**: emitter completion/timeout triggers a Tomcat ASYNC dispatch that re-enters the security filter chain without a security context; the committed event-stream can't take a 401, so Spring logs an ERROR. Fix: include `DispatcherType.ASYNC` in the `dispatcherTypeMatchers(...).permitAll()` line (safe — an async dispatch only follows an already-authorized request).
- **`@Version` jumps by more than 1**: mutating entity fields before a repository query in the same method causes Hibernate AUTO flush to write the entity twice. Fix: run all reads first, then apply all mutations right before the final `save`/`saveAndFlush`.
- **`npx tsc --noEmit` in `src/main/frontend` type-checks NOTHING and always exits 0**: the root `tsconfig.json` is solution-style (`"files": []` + `references` to `tsconfig.app.json` / `tsconfig.node.json`), so `--noEmit` has no files to check. Any "tsc --noEmit is clean" claim proves only that the command ran. The real type gate is **`npx tsc -b`** (what `npm run build` runs). Verified 2026-08-17 — `tsc --noEmit` stayed silent on an error `tsc -b` reported.
- **Files hand-placed in `src/main/resources/static/` disappear**: the Vite build (`outDir: '../resources/static'`, `emptyOutDir: true`) wipes that directory on every frontend build. Static public files (favicon etc.) go in `src/main/frontend/public/` — Vite copies them to the static root; dynamic ones (robots.txt, sitemap.xml) are served by controllers.
- **`@Modifying(clearAutomatically = true)` mid-transaction silently discards pending inserts (workspace vanishes / `WorkspaceNotFoundException`)**: a bulk UPDATE only auto-flushes entities whose *tables* the query touches, so unrelated pending inserts stay queued; `clearAutomatically` then `em.clear()`s them away before they're written. Bit `WorkspaceService.create` when `UserRepository.markOnboarded` (a bulk UPDATE on `users`) was `clearAutomatically=true` — it wiped the just-`save`d workspace+member, so the workspace was never inserted (broke all workspace creation, surfaced via first-login demo seeding failing at `ProjectService.resolveWorkspace`). Fix: only use `clearAutomatically` when you actually re-read the mutated entity in the same transaction (e.g. `claimDemoSeed`, called before any other pending writes); otherwise plain `@Modifying`. If you need both, add `flushAutomatically=true` so pending inserts are flushed before the clear. Guarded by `WorkspaceCreationTest`.
- **`@Modifying` JPQL update not visible to subsequent `findById` in same transaction**: Hibernate L1 cache returns the stale entity after a bulk UPDATE. Fix: `@Modifying(clearAutomatically = true)` — clears the first-level cache after the update so the next read hits the DB (but see the pending-inserts trap above — don't clear mid-transaction after saving unrelated entities). Note: for increment-then-read (issue sequence numbers) even that is racy — two transactions can re-read the same final value. `ProjectRepository.incrementAndGetIssueSeq` uses a native `UPDATE ... RETURNING` instead, which gives each transaction its own value.
- **A native-counter column silently reset by a later entity `save()` (issue numbers collide)**: `projects.issue_seq` is bumped by the native `incrementAndGetIssueSeq` (`UPDATE … RETURNING`), which does NOT refresh the managed `Project` in the persistence context. If the same transaction later mutates and saves that stale `Project` (demo seeding did `findById` → `setFieldSet` → `save` after creating 20 issues), Hibernate flushes the entity's stale `issue_seq` (0) and overwrites the DB counter — so the next created issue reuses `number = 1` and 500s on `duplicate key … issues_project_id_number_key`. Fix: mark the column `@Column(updatable = false)` so JPA never writes it (only the native increment does); repair already-desynced rows with a migration that resyncs `issue_seq` to `MAX(number)` (V9). General rule: any DB-maintained counter written by native SQL must be `updatable=false` on the entity, or a stale managed copy will clobber it.
- **"Replace children wholesale" update (`deleteAllBy…` then re-`save`) violates a UNIQUE constraint**: within one flush Hibernate orders INSERTs *before* DELETEs, so re-inserting a row with the same unique key (e.g. `UNIQUE(workflow_id, status_id)`) collides with the not-yet-deleted old row. Bit the admin set editors (`AdminWorkflowService`/`AdminPrioritySetService`/`AdminIssueTypeSetService`/`AdminFieldService.updateSet`) — editing an existing workflow/set 500'd. Fix: call the child repo's `.flush()` between the `deleteAllBy…` and the re-insert.
- **Admin error messages invisible in the UI (blank banner, "nothing happens")**: admin services throw raw `ResponseStatusException`, whose reason is only serialized to the client when `spring.mvc.problemdetails.enabled=true` (default false — was unset). Without it the body has no `detail`/`message`/`title`, so the SPA's `request()` fell back to `res.statusText` (empty over HTTP/2) and rendered nothing. Fixed by enabling problemdetails in `application.properties`; `request()` also now falls back to `Request failed (<status>)` so no error is ever silent.
- **RFC 9110 status renames — the old constants AND MockMvc matchers are deprecated (Boot 4 / Spring 7)**: 422 "Unprocessable Entity" → "Unprocessable Content" (`HttpStatus.UNPROCESSABLE_CONTENT`, matcher `status().isUnprocessableContent()`); 413 "Payload Too Large" → "Content Too Large" (`HttpStatus.CONTENT_TOO_LARGE`). The old `UNPROCESSABLE_ENTITY`/`PAYLOAD_TOO_LARGE` constants and the `isUnprocessableEntity()` matcher still resolve to the same codes but are deprecated — use the new names in new code (same codes, `isUnprocessableEntity()` matcher still matches at runtime but compiles a deprecation warning). Also deprecated: `org.springframework.lang.@NonNull/@Nullable` (Spring 7 → JSpecify) — drop them on override params or switch to `org.jspecify.annotations.*`.
- **Project delivery capabilities are declared on `projects`, never inferred from data presence; capabilities gate UI only, never the API.** `board` / `releases` / `estimation` are columns (V12); `preset` is derived server-side and rejected on write. Never decide what to show by counting existing rows — "the project has a sprint, so it must do Scrum" is the exact bug this model was built to delete, and it shipped once already. And never let a capability change a status code: a hidden control is not a permission, so a project with `releases` off must still accept and return version data. Every capability also needs an enabling affordance visible *while it is off* (Rule C) — otherwise the feature is unreachable for anyone who does not already use it. Full model: `docs/design/delivery-paths-proposal.md`. The reports epic re-proved the API half: a capability narrows what the UI *offers* and never what the server *resolves* — a slice the panel hides still answers if a saved URL asks for it.
- **`issues.position` is the project-wide backlog rank** — server-written only, spaced by `RANK_STEP` (2^26), computed from neighbour anchors (`afterIssueId`/`beforeIssueId`), and rebalanced by a native whole-project renumber that runs `SET LOCAL hamstrack.skip_updated_at = 'on'` first so it stamps neither `updated_at` nor `@Version`. Never write it from a client payload, and never expose it in a response. The rebalance is throttled per project (429 + `Retry-After`) because ~26 cheap drops into one gap can otherwise force an unbounded number of whole-table rewrites.
- **`DB_URL` silently ignored when running the app locally**: `spring-boot-docker-compose` is on the classpath, so it starts/attaches the compose Postgres and **overrides the datasource** — a `DB_URL=…` run quietly hits the compose database instead of the one you named. Pass `--spring.docker.compose.enabled=false` when you need to point at a specific DB (e.g. verifying a migration from scratch).
- **Primitive `boolean` (or any primitive) in a request DTO record → 400 on any body that omits it (Boot 4 / Jackson 3)**: Jackson 3 enables `FAIL_ON_NULL_FOR_PRIMITIVES`, so a partial PATCH/POST whose JSON omits a primitive field fails deserialization (`Cannot map null into type boolean`) and surfaces as `400 {"detail":"Failed to read request"}`. Bit `UpdateIssueRequest`'s `clearAssignee`/`clearDueDate`/`clearParent` flags — every partial issue update 400'd. Fix: use the boxed type (`Boolean`) for optional request fields and coalesce null→default in a compact canonical constructor (`this.flag = flag != null && flag;`). Applies to any optional numeric/boolean field in a create/update record.
- **A `catch` around `save()` never fires — the INSERT is deferred to commit.** Spring Data's `save()` only queues the persist; Hibernate flushes at commit, *after* the `@Transactional` service method has returned, so the `DataIntegrityViolationException` is raised outside every `try` in that method and a constraint violation you meant to translate stays a 500. Use **`saveAndFlush`** whenever a constraint violation must become a status code (HD-133's `DUPLICATE_INVITE` 409, HD-167's registration 409). The corollary is the one that bites later: a translation `catch` that is never entered looks identical to one that works, because both produce no error in the happy path — so seal it with a test that forces a real violation, not with a code review.
- **A claim phrased about a *category* outlives a claim phrased about a *member*.** The reports epic (HD-5) corrected every stale *enumeration* across four review rounds and missed every stale *uniqueness* claim, because "only", "one place", "the only bound", "inherits", "always" are counts that a new path invalidates **while containing none of the words a grep for the new path would find**. Two sentences that happened to be written as a property of a *class* survived every change untouched; four written about one member had to be fixed, and one was still false a slice later ("the only endpoint here with no `400` of its own" — until its own `.csv` sibling shipped). When you write a doc, javadoc or failure message, prefer *"a report that asks the caller for nothing has nothing to refuse"* over naming the one report that does it today. Same rule kills the leading count: **a number goes stale one entry before the list does** — the epic shipped two lists that undercounted themselves, one of them written past a comment forbidding exactly that.
- **`sprint_scope_events.issue_id` is nullable, so a reader must NEVER inner-join `issues`.** The FK is composite `(issue_id, workspace_id)` with `ON DELETE SET NULL (issue_id)` (V18) — deliberately not `CASCADE`, because a cascade loses an issue's *arrival and departure as a pair* and a completed sprint would quietly shed issues while its scope arithmetic still balanced. The row keeps a snapshotted `issue_key` and `story_points` so a departed issue still renders. An inner join silently drops exactly the rows the design exists to preserve. Group by `issue_id`, **or by `issue_key` when it is null**, or every departed issue in a sprint collapses into one phantom whose adds and removes interleave.
- **A throttle is earned by the work a handler does, not by where it is mounted.** Insights inherited no budget at all because the limiter was bound to `…/reports/**` and it hangs off `/search` — "inherited by construction" held for five slices and failed silently the moment an endpoint moved. Fixing that exposed the wider hole: `POST …/search` was itself unbudgeted while doing *more* work (50 leaf predicates, each `text ~` two unanchored `LIKE`s, run twice per request), so anyone wanting to saturate the pool had no reason to use the throttled path. Saved-filter CRUD is on the search budget for the same reason — validating a filter's HQL builds the same `ResolutionContext` `/search/schema` pays for. **The throttled path set is sealed by a test whose failure message is the propagation checklist**; a new expensive surface is a deliberate edit there, never an omission.
- **Authorization is one resolution and one primitive (HD-123, complete).** `WorkspaceAccessService.resolveProject` (renamed from `requireProjectMember`, which never read `project_members`) verifies *workspace* membership and finds the project inside it, and resolves **once per request** an immutable `PermissionSet` onto `WorkspaceContext`/`ProjectContext`. A call site authorizes with one line — `ctx.permissions().require(Permission.SPRINT_MANAGE)` (403 `MissingPermissionException`, detail names the permission). Cost is constant: **2** statements workspace-scoped, **4** project-scoped, **0** to check (`PermissionResolutionQueryCountTest`). The 29-permission catalog is the `common.security.Permission` enum — **there is no `permissions` table**; adding one is an enum constant + a `require(...)` + a seed row, never a migration. `WorkspaceRole`, `ProjectRole` and `ScopeResolver` are **deleted**; surviving mentions are prose. Roles are rows: built-ins are shared (`workspace_id IS NULL`), custom ones belong to a workspace, and **creation is duplicate-only** — no bare `POST /roles`, because the grant ceiling is a **subset** rule ("everything you hand out, you hold", `PermissionSet.firstNotCovered`, compared per grant *width* so unrestricted is not covered by own-only), and a role composed from an empty checklist can assign nobody. **The workspace Owner is the root of trust**: above the ceiling in their own workspace for both defining and assigning, keyed on the built-in Owner **role id**, never the key string. Hard-won rules, each of which cost a review round: (a) never re-query `workspace_members`/`project_members` for an authorization decision — the answer is on the context; (b) **never drop `JOIN FETCH m.role`** from a membership finder; (c) `RolePermissionCache` is a separate bean because `@Cacheable` is proxy-applied and self-invocation bypasses it; (d) tenancy comes first — non-existence and non-membership are both **404**, 403 only for a proven member. **A role id asks two questions — whose workspace, and which scope.** `PermissionSet` is a flat `EnumSet` with no memory of provenance, so a WORKSPACE role in `project_members.role_id` puts `workspace.edit` into that member's `ProjectContext`, and a PROJECT role carrying a workspace permission does the same — hence **422 if a permission's scope ≠ its role's scope**, and request-supplied role ids resolve only through `RoleRepository.findAssignable(id, workspaceId, scope)` (`RoleRepository` deliberately does not extend `JpaRepository`, so a bare `findById` will not compile). Collection reads *degrade* a corrupt row to `role: null` **and** `roleId: null` — emitting the id hands back the withheld name by proxy; single-resource writes *refuse* instead. **Unknown permission keys: 422 on write, log-and-drop on read** — `PermissionConverter` runs inside `requireMember` on every authenticated request, so dropping narrows a role while throwing takes down the instance. **A key is not an identity**: `MEMBER` names two different built-ins across scopes, so match members to roles by `roleId`. **The ceiling must be checked at BOTH ends of every change** — the role being granted *and* the one being replaced; checking only the new one lets an Admin demote an Owner, and this was missed once on membership and again on role edit/delete. **Holding a role has two mechanisms, not one**: an explicit `project_members` row, and the default-access chain (project default → workspace default → built-in Contributor, only while the workspace is `OPEN`). A guard that tests one and not the other is the shape of this epic's Critical — "set the default narrow, then widen the role" reached all twenty project permissions in three calls. `project_access_mode` decides **only** whether non-members inherit; there is deliberately no enforcement-off branch, and exactly one `mode != OPEN` test exists in the codebase (`WorkspaceAccessService.fallback`) — `defaultProjectRole` is mode-aware and is what a new caller wants, `declaredDefaultProjectRole` ignores the mode and has two permitted callers. **A project with no holder of `project.member.manage` is unmanageable by anyone, including a workspace Owner** (it is outside `projectCuration()`), so nine separate doors are guarded — three locked, six advisory because an aggregate cannot take `FOR UPDATE`, and the javadoc says which is which. **A refusal may only prescribe an action its reader can perform**; this epic shipped that mistake three times, so a 409/403 that names a remedy must name one reachable by its recipient, and carry the projects when the reader cannot otherwise tell which is at fault. **Caching**: a role's *contents* live in a 10 s per-node Caffeine cache evicted after commit, so a revocation can survive ~10 s on another replica; membership, the access mode and both default-role columns are **not** cached and bite on the next request everywhere. **Locks**: every transaction taking a row lock calls `LockTimeout.applyToCurrentTransaction()` first (bound, then lock) — and use `FOR NO KEY UPDATE`, not `FOR UPDATE`, on `workspaces`, or every FK child insert in the tenant blocks behind it.
- **BCrypt refuses to *create* a hash above 72 UTF-8 bytes but silently truncates when *checking* one, so a password bound belongs on the writing doors in BYTES and must NOT be tightened on the reading door.** `BCrypt.hashpw` throws `IllegalArgumentException: password cannot be more than 72 bytes` (`if (!for_check && passwordb.length > 72)`); `matches` passes `for_check = true` and compares the truncated prefix. So `@Size(max = 100)` on `RegisterRequest.password` / `ResetPasswordRequest.newPassword` produced an unauthenticated **500** for a 73–100-character ASCII password — and, because the limit is bytes, from **37 characters of Cyrillic**, 25 of CJK, 19 of emoji (HD-171). `@Size` counts UTF-16 units and the encoder counts bytes, so the annotation is only half the guard: pair it with a UTF-8 byte check (`PasswordLimits.exceedsEncoderLimit`, 422) placed **before** any token is looked up or burned. `LoginRequest.password` is deliberately `@Size(max = 1024)` with **no `min`** — a login door must accept whatever password any writing door produced (a bound justified by enumerating those doors goes stale; this one did, on its third door), and a `min` there answers 400 where the endpoint must answer 401, which is an oracle.
- **Never put `@Validated` on a bean Spring MVC dispatches to** (`@Controller`/`@RestController`/`@ControllerAdvice`) — ADR-0018. `HandlerMethod.shouldValidateArguments()` returns `false` when the bean type carries it, so MVC skips its own method validation and the AOP proxy throws `jakarta.validation.ConstraintViolationException` instead of `HandlerMethodValidationException`. That gave one controller a different refusal mechanism than its siblings: `SearchController` carried it, and its `@Size(max = 100)` on `q` answered **500** from HD-3 until HD-214 removed it — the annotation and the bound landed in the same commit and no test ever sent an over-long value, which is why it stayed green for months. The exception is now caught (fully qualified, or it shadows the Hibernate `ConstraintViolationException` bound in the same class) and answers 400, **but it logs at ERROR on purpose**: reaching that backstop means a web bean grew the annotation again. So the prohibition is about one refusal shape for every declared constraint, not about a crash. `@Validated` on the ten `@ConfigurationProperties` classes is **correct** and must stay — it validates binding at startup, where no dispatch is involved. Bounding a query param is one annotation; adding `@Validated` to make it "work" is what breaks it. Sealed by a category test over every web bean, with a tripwire on the number scanned.
- **`ddl-auto=validate` does NOT compare column lengths.** Hibernate's schema validator calls `ColumnDefinitions.hasMatchingType` (JDBC type code, or the type name with arguments stripped); `hasMatchingLength` exists but is reached only from `StandardTableMigrator`, i.e. `ddl-auto=update`. So `VARCHAR(50)` in the database against `@Column(length = 100)` on the entity **boots clean and fails at INSERT**. Verified against hibernate-core 7.4.1 and 7.2.12. An entity/schema width pair is therefore kept equal *by hand*, and the only thing that catches a drift is a behavioural test in the narrowing direction plus an `information_schema.columns` parity assertion in both (HD-171). Never write "validate will catch it" in a migration header — a header promising a net that is not there makes the next reader stop checking.
- **A value the server DERIVES from another column has no DTO to annotate, so bean validation cannot see it.** Both 500s HD-171's sweep found were of this shape: `workspaces.slug` derived from a `@Size(max = 255)` name into `VARCHAR(100)`, and `issue_history.field` fed a custom field's *display name* (`VARCHAR(100)`) into a `VARCHAR(50)`. A perfect DTO→column scanner scores a clean pass over both. Rules: (a) a derived value is either bounded by its target column's width or truncated at the write site, and the truncation belongs on the **entity setter**, not in one service — `issue_history` has four writers and the belt was first installed on one; (b) when a collision suffix is appended, carve it **out of** the width, not on top, or a near-miss length still overflows; (c) the guarantee is a **behavioural** category test asserting a status *class* (4xx, never 5xx) per write endpoint — `RequestFieldLengthBoundTest`, whose second tripwire reflects over every `@PostMapping`/`@PutMapping`/`@PatchMapping` rather than listing them.
- **A green unfiltered `mvnw test` is not evidence unless the class count was checked.** A run once reported `Tests run: 1463, Failures: 0, Errors: 0, Skipped: 0` and BUILD SUCCESS while executing 224 of 252 test classes, saying nothing whatsoever about the other 28 — a contiguous alphabetical prefix of whole packages, one of which held the class the author had just written. It was caught only by a remembered total looking low, which is not a mechanism. *"A filtered run is not evidence"* was already lore; the honest version is that **an unfiltered one is not either**. Since HD-265 the `test-tree-coverage-guard` antrun execution fails such a run and **names the absent classes**: a `TestExecutionListener` records what actually ran (immune to test selection) and the build step refuses (no test selection can reach it) — a guard shaped as a test class would be dropped by the very truncation it guards against. The bound is derived from **test-named sources**, never from `target/test-classes` (a truncated compile would truncate the bound in the same stroke and agree with the bug) and never from `target/surefire-reports` (cumulative, never cleaned — it has held reports for classes deleted weeks earlier). It disarms honestly for `-Dtest=`/`-Dgroups=`/`-DskipTests` and for IDE runs. **Corollary that will bite you:** nothing under `src/test/java` may be named `Test*`, `*Test`, `*Tests` or `*TestCase` unless it really is a test — those are Surefire's includes and therefore the guard's bound, so a helper wearing one of those names is demanded as a class that must execute. The guard deliberately does **not** excuse a class for lacking `@Test`: one inheriting its tests from a base declares none, and that filter would silently shrink the bound into a better-hidden copy of the original bug. The cause of the truncation itself was never reproduced and is still open.

Run the app / tests (PowerShell):
```
$env:DB_URL="jdbc:postgresql://localhost:15432/hamstrack"; $env:DB_USERNAME="hamstrack"; $env:DB_PASSWORD="hamstrack"; $env:JWT_SECRET="dev-only-jwt-secret-hamstrack-0123456789abcdef"; .\mvnw.cmd spring-boot:run
```
`JWT_SECRET` must be at least 32 bytes — `JwtService` fails fast at startup otherwise (HMAC-SHA256 key size requirement).

**`-Dfrontend.skip=true` really skips the frontend build** (HD-94, 2026-08-17 — it was a no-op before that): `pom.xml` declares a `frontend.skip` property (default `false`) bound to `<skip>` in the `frontend-maven-plugin` configuration, and every goal of that plugin has its own editable `skip` parameter, so **all four** executions (`install-node-and-npm`, `npm-install`, `npm-build`, and `npm-test` since HD-242) log `Skipping execution.` — use it for a fast backend-only loop (the SPA build alone was ~24s saved per invocation with a warm npm cache, far more on a cold one; since HD-242 it also drops the ~45-70s frontend suite). Leave it **off** for anything that must ship the SPA — or that must *test* it: a plain `mvnw package` and CI's single `./mvnw -B verify` still build `src/main/frontend` into `src/main/resources/static` → `BOOT-INF/classes/static/` in the JAR, and since **HD-242** the `npm-test` execution (bound to the `test` phase, so `-DskipTests` switches it off exactly like surefire) runs `vitest run` inside that same command — before it, the whole frontend suite ran on no automated path at all. Budget ~45-70s for it on a non-skipped build. In PowerShell, prefix args with `--%` so `-D` flags aren't mangled. **On Windows, stop the Vite dev server before any build that includes the frontend** — `pom.xml` runs `npm ci`, which deletes `node_modules` first, and a running dev server holds `lightningcss.win32-x64-msvc.node`, so the delete fails with `EPERM` and takes the whole Maven build down. It surfaces as an opaque mid-build error on a command you didn't run; `-Dfrontend.skip=true` avoids it entirely. Linux CI is unaffected.

## Subagents

Project subagents live in `.claude/agents/*.md` (all `model: inherit`). Reviewers are read-only (`Read/Grep/Glob/Bash`); builders and the doc/test agents can edit. Invoke explicitly (e.g. "use migration-reviewer for V11") or let them trigger on their `description`.

**Project-native agents (★ — prefer these for anything touching Hamstrack code/config/schema/API):**

- **`systems-analyst`** — turns fuzzy feature requests into a precise spec (scope, actors/permissions, rules, edge cases, data-model/API/frontend impact, DC/Cloud implications, acceptance criteria) written to `docs/design/`. Run it BEFORE building; it does not touch code.
- **`tenancy-reviewer`** — reviews backend diffs for cross-tenant leaks (unscoped queries, missing membership checks, 403-instead-of-404, parent re-verification in nested paths). Run it after touching any workspace-scoped repository/service/controller — this is the project's top bug class.
- **`security-officer`** — app-sec review of everything EXCEPT cross-tenant isolation (that's `tenancy-reviewer`): authn/JWT, authz/roles, account & reset flows, rate limiting, file upload/download, injection/SSRF, input validation, secrets/config leaks, dependencies. Run it after touching auth, admin, uploads, or config.
- **`migration-reviewer`** — checks new Flyway migrations + entity mappings against the documented Hibernate 7 / PG pitfalls (no `CHAR(n)`/ENUM, `updatable=false` counters, UUID v7, `@CreatedDate`, entity⇄schema parity, never edit an applied migration).
- **`dc-cloud-guard`** — enforces the single-codebase-two-modes rule (profile/property-gating, no forked logic, no cloud-only assumptions) and the full env-var wiring checklist (properties → compose → `.env.prod.example` → README).
- **`api-docs-sync`** — on any API change, syncs `openapi.yaml` + both `docs/api-*.md` and validates with swagger-cli.
- **`backend-builder`** — implements Spring Boot 4 features by package-by-feature convention with the mandatory Hibernate/Jackson/`@Version`/`@Modifying` patterns baked in. **The only agent that writes backend code.**
- **`frontend-builder`** — implements SPA features (React 19 / Tailwind v4) with the `max-w-*` shadow trap, splat-route absolute paths, and config-driven rendering baked in; reads `DESIGN.md` first. **The only agent that writes frontend code.**
- **`test-runner`** — runs/writes the suite with the correct env (creds `hamstrack`/`hamstrack`, port 15432, `-Dfrontend.skip=true`) and Boot 4 test-import quirks.

Two **imported families** (general-purpose from `piomin/claude-ai-spring-boot`, specialist from `VoltAgent/awesome-claude-code-subagents`) are **read/advise fallbacks** for broad or deep single-topic questions — full catalog in `docs/project-state.md`. They do NOT know the tenancy/migration/DC-Cloud rules and must never implement code (the 7 generic *implementers* were deleted on 2026-08-14 for exactly that risk).

**Routing rule:** for any task that touches Hamstrack code, config, schema, or its API, use a **project-native** agent. Imported agents are fallbacks only; when more than one could apply, the project-native one wins (it knows the top bug class — cross-tenant data leaks). **Only `backend-builder`/`frontend-builder` write code.**

## Dev pipeline (orchestration, 2026-08-14)

The subagents run as a **dev team on autopilot**: the main session is the **orchestrator** (a subagent can't spawn subagents — star topology, not a tree) and delegates a task through mandatory + conditional review gates. Full spec: `docs/design/dev-team-pipeline.md`.

- **Skill `feature-pipeline`** (`.claude/skills/feature-pipeline/SKILL.md`) — the orchestrator playbook: classify (feature / light / trivial), delegate, run gates, maintain the gate file. Invoke it for any non-trivial change; it's the soft layer (routing + phases).
- **Mandatory gates:** `systems-analyst` (spec, before code) · `tenancy-reviewer` (any backend diff) · `security-officer` (features) · `test-runner` (features/light). **Conditional:** `migration-reviewer` (migration/`@Entity`) · `dc-cloud-guard` (`*.properties`/profile/compose/env) · `api-docs-sync` (REST surface). **Routing invariant:** only `backend-builder`/`frontend-builder` write code.
- **Hard layer — Stop hook.** `.claude/pipeline/check-gates.mjs` reads the per-task gate file `.claude/pipeline/run.json` (gitignored transient state) and **blocks the session from finishing** until every required gate is `pass`/`n/a`. It **recomputes touched areas from the real `git diff`** (so under-declaring scope can't skip tenancy), and forces reclassification if a `trivial` run actually touches code. A hook can only block+remind, never dispatch — the orchestrator's next turn dispatches the missing agent.
- **Manual bootstrap (once):** `settings.json`/`settings.local.json` are agent-write-denied, so the `Stop` hook registration is added by the user (it is registered in `.claude/settings.local.json`). Without it, gates degrade from enforced to convention.
- **Autopilot policy:** spec proceeds without an approval pause (user vetoes after); fix loop capped at 3 rounds per gate then escalates.
