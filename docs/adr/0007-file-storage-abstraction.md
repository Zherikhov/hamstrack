# ADR-0007: File storage behind the `FileStorage` abstraction (local/S3)

Record date: 2026-08-22 (retrospective; the decision was made earlier)
Status: Accepted
Source: `CLAUDE.md` → the "DC vs Cloud (single codebase)" section → File storage

## Context
Attachments have to be stored in both delivery models: self-hosted (DC) usually has no
S3, Cloud does. Addressing a concrete storage backend directly from the code would
tie the application to one model.

## Decision
A single `common.storage.FileStorage` interface; the backend is selected by the
`app.storage.type` property (`local` | `s3`). Defaults by profile: `dc` → the local FS
(`app.storage.local.base-dir`, by default `./data/attachments`, gitignored),
`cloud` → S3 (`app.storage.s3.*`: bucket, region, optionally `endpoint` +
`path-style-access` for MinIO/S3-compatible stores, optional static keys —
when they are empty the AWS SDK default credentials chain is used).

The implementations (`LocalFileStorage` / `S3FileStorage`) are beans gated by
`@ConditionalOnProperty`. The code injects the **interface** `FileStorage`, never
a concrete class. Storage keys are generated by the server
(`ws/{wsId}/issues/{issueId}/{uuid}`); the original file names live only in the
DB. The upload size limit is `spring.servlet.multipart.max-file-size` (env
`ATTACHMENT_MAX_FILE_SIZE`, 25MB by default).

## Consequences
+ The very same attachment logic works both in DC (local FS) and in Cloud (S3).
+ Changing the backend is a matter of config, not of code.
+ The server-generated storage keys do not reveal the original file names.
− Every new storage backend is one more implementation of the interface.

## Alternatives
- Addressing S3 directly from the code — rejected: it breaks the self-hosted model that has no S3.
