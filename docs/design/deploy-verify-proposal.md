## 1. Problem & goal
Every step of a deploy today reports what it *did*, none reports what the box *is*. Four retro incidents were each visible to a read-back nobody performed. Goal: a `verify` phase at the tail of `ops/deploy/apply-config.sh` that reads the **running** state, exits non-zero on a mismatch, is loud in the Actions log, and publishes a gauge an alert rule reads — plus a read-only pre-flight that reports what the deploy is about to change *before* it changes it.

## 3. Scope / non-goals
**In:** `preflight` (read-only, before step 4) and `verify` (after step 9) in `apply-config.sh`; a pessimistic `hamstrack_deploy_verify.prom` written at the first mutation and rewritten at the end; rule `DeployVerifyFailed`; `deploy.yml`: replace the 100-s `wait` with a bounded poll, pass a regex-validated ref, print the two bodies as text; tests (§9); doc rows. **Out (Should half, may land separately):** the synthetic delivery drill of `DeployVerifyFailed` (HD-298's drill log takes the row). **Out:** any rollback, any change to what the drift script publishes, Prometheus/Loki health, comparing env *values*, Caddyfile content.

## 4. Where it attaches, and what runs before the mutation
- **Pre-flight (new, between 2b and 3, also printed by `--dry-run`)**: `docker compose --project-directory $TARGET --env-file $TARGET/.env $VALIDATE_ARGS up -d --dry-run 2>&1` (the drift script's oracle, drift.sh:456) — logged as *service → verb* pairs and the orphan line, names only; plus per service `declared ceiling (release) vs running HostConfig.Memory`. **Never fatal** (a mid-outage plan aborts on an unhealthy dependency, drift.sh:483–507; the deploy exists to fix what this reports). This is the HD-199 read-back moved *ahead* of the change: on 2026-08-26 it would have printed `app Recreate`, `postgres Recreate`, `caddy Recreate` and three `0 → …` ceilings against a log claiming nothing to do.
- **Verify (new step 10)**: after step 9, before `deploy complete`. It needs 7b's restarted Grafana and 9's fresh gauges, so nothing can sit after it. Any failure → `die` → exit 1 → SSM command fails → job red with bodies (deploy.yml:134–139). `rm -rf $SYNC` is skipped on failure (`set -e` in the SSM script); the day-old sweep at deploy.yml:113 bounds the residue.
- **Tools**: `need_tool jq` and `need_tool curl` are added at :132–136 so a box lacking them is refused **before** step 4, never at step 10 (curl is proven on prod by deploy.yml:115; jq is **inferred** — §11).

## 5. What a red verify means — the text every check ends with (≤ 25 lines total with the check's own line)
`VERIFY FAILED: <check>: <one-line finding>. The configuration from $SHA IS APPLIED and stamped, the containers WERE brought up; nothing is rolled back (by decision — a deploy never reverts itself). Production may be half-updated: read the finding, then EITHER fix forward (correct .env / the file and push, or re-run this deploy — it is idempotent) OR return to the previous state by hand: previous synced files are in $BACKUP_DIR (or "no path changed, so no backup was taken"), the previous image is pinnable with APP_IMAGE_TAG=<previous tag> in $TARGET/.env, then 'docker compose -f … up -d' in $TARGET (§6.4). Until a later deploy verifies green, DeployVerifyFailed stays firing.`

- **Corrected in the HD-299 fix loop — TWO paragraphs, one per mode.** The text above is the DEPLOY one, and every clause of it is false after `--verify-only`, which places nothing, stamps nothing, pulls nothing and brings nothing up: it has no backup directory from "this run" and no "image running before this run" to pin, and "production may be half-updated" is the sentence that sends somebody hunting for a rollback after a read. The read-only paragraph says what was and was not done and offers the two remedies that reader can perform. **The remedy is stated in the refusal and nowhere else**: `DeployVerifyFailed`'s annotation used to carry the deploy paragraph verbatim, for an alert that also fires from a `--verify-only` run, so it now states which run wrote the 0 is something only the applier's own output can say and sends the reader there.

## 7. The alert half (the mechanism the box already has: node-exporter textfile)
- File `hamstrack_deploy_verify.prom`, same dir/atomic write/0644 as drift.sh:134–168; written **pessimistically at the start of step 5** (`hamstrack_deploy_verify_ok 0`, every `hamstrack_deploy_verify_check_ok{check} 0`, `hamstrack_deploy_verify_timestamp_seconds now`, `hamstrack_deploy_verify_info{sha}`) and rewritten by verify with the real results — so a deploy killed between 5 and 10 leaves a 0 behind instead of last week's 1 (the backup script's lesson, backup.sh:99). `check` is a closed enum of the five names above. Write failure → WARN, never fatal (a metric that cannot be written must not red a good deploy — step 9's rule).
  - **Fix loop:** the per-check values are `0` failed, `1` passed, **`2` not applicable on this box** — one value for the last two made a crash-looping Grafana nobody asked about read exactly like a Grafana that was checked. And **a check that did not read the box may only lower confidence, never raise it**: writing `2` over a `0` a previous run READ is refused in `_check_ok`, the one place a value is written, so the documented `COMPOSE_FILES=…` narrowing cannot silence a firing critical alert (measured: it silenced four and printed `PASS 5/5`). The discriminator for "read as failing" vs "not run yet", which share the value `0`, is the previous file's `checks_ran`.
- Rule `DeployVerifyFailed`, uid `hamstrack-deploy-verify-failed` (30 chars), expr `hamstrack_deploy_verify_check_ok`, threshold `< 1`, `for: 5m`, `severity: critical`, `noDataState: OK`, unaggregated so the summary names `{{ $labels.check }}` and sends the reader to the deploy's Actions log and §5's two remedies. No staleness rule: this is not a timer, and "no deploy lately" is not a finding.
- Log half: the Actions job is red with the bodies printed as **text** (two separate `--query StandardOutputContent`/`StandardErrorContent … --output text` calls, not one JSON blob whose `\n` are escaped).
  - **Corrected in the HD-299 fix loop.** The limit is no longer inferred: **measured** 2026-09-10 from the bundled AWS service model (`botocore ssm/2014-11-06/service-2.json`) — `StandardOutputContent` is `{"type":"string","max":24000}`, documented as *"The first 24,000 characters written by the plugin to `stdout`"*, and `StandardErrorContent` is `max: 8000`. It is the **first** characters, not the last, and this line's "verify's lines are the last ~25 of stdout, inside the capture" was the wrong half of that: a deploy long enough to overflow loses exactly the conclusion. Fix: the noisy middle is quietened at source (`compose pull --quiet`, `docker image prune -f >/dev/null`) and every refusal plus the final `verify: PASS|PARTIAL …` summary is **mirrored to stderr**, which carries only Compose's own progress. `rules.yml` no longer tells the reader that a log stopping early means a killed deploy — it sends them to the stderr group first.

## 8. `deploy.yml` changes (measured need, §2 row 3)
1. Replace `aws ssm wait command-executed` with a poll of `get-command-invocation` `Status` every 10 s until ∉ {Pending, InProgress, Delayed}, bounded at 20 min, `--timeout-seconds 1500` on `send-command`. Without this, verify's polling budget alone (≤ 180 + 90 + 20 s) makes a good deploy red. **`--timeout-seconds` is a DELIVERY bound and never an execution one** — measured 2026-09-10 from `SendCommandRequest.TimeoutSeconds` in botocore's ssm model: *"If this time is reached and the command hasn't already started running, it won't run."* Nothing in this workflow kills a command that has started; the poll's own 20-minute deadline is what bounds the job. The alternative — passing the `AWS-RunShellScript` document's `executionTimeout` parameter — is a real kill switch and is deliberately not taken, because it cannot be measured from this repository and a wrong parameter name fails every deploy at `send-command`.
   - The success echo (added in the fix loop): one line, `verify: PASS|PARTIAL ran=<read>/<declared> skipped=… services=… env-services=… app-identity=… withheld=… sha=… version=…`, selected out of the box's output by the `VERIFY_SUMMARY_ANCHOR` regex. The verdict word is `PARTIAL` whenever fewer than the declared checks read the box — `PASS <n>/<n>` was the declared count over itself on every run that reached the line, so a box that verified almost nothing announced `PASS 5/5`. **By anchor, never by substring** — the Actions log is world-readable and `verify: WARN drift-fresh: edge-body-limit=1` names a live weakness of the production edge. `ApplyConfigVerifyPhaseTest` holds both halves: the applier emits the line, and the anchor cannot match a WARN or a FAILED line.
2. Pass `EXPECTED_APP_VERSION` into the SSM command **only** when `HEAD_REF` matches `^v?[0-9]+(\.[0-9]+)+$` (then `${HEAD_REF#v}`); `main` passes empty; anything else fails the step before `send-command` — a ref never reaches the shell unvalidated (deploy.yml:98–102 keeps that rule).
3. "Report deployed version" stays (public summary) — it does not verify and must not be read as if it did.
