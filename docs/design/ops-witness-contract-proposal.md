## 5. Production changes (all arm `tenancy` + `security`; none touches a query or a tenant row)
### 5.1 `common.observability.ScheduledJobHeartbeat` — one class, zero edits to the 13 annotated sites
- **Branch A (inferred, measure first — §11.1):** Boot 4 auto-observes `@Scheduled` (`tasks.scheduled.execution`, tags `code.function`/`code.namespace`, via `ScheduledTasksObservabilityAutoConfiguration`). Then the heartbeat is an `ObservationHandler<ScheduledTaskObservationContext>` bean: `onStop` sets `last_run` and, on `context.getError() != null`, increments `failures`. **Branch B:** no observation → the heartbeat is a `BeanPostProcessor` calling `ScheduledAnnotationBeanPostProcessor.setObservationRegistry(registry)` plus the same handler. Either way the 13 sites are untouched, which is the retro's "share it, never copy it".
- `SmartInitializingSingleton`: read `ScheduledAnnotationBeanPostProcessor#getScheduledTasks()`, register per task `last_run` (seeded `Instant.now()` — the ProductMetrics:354–370 precedent, *never* 0/-1) and `period_seconds` (`IntervalTask.getIntervalDuration()`; `CronTask` → gap between the next two `CronExpression` fire times). Label `job` = `SimpleName#method` (bounded: 14 values; the `Handler.id()` spelling).
- `StorageReconcileSchedule:54` becomes `registrar.addCronTask(heartbeat.wrap("WorkspaceStorageReconciler#reconcile", reconciler::reconcile), cron)` — the one explicit call, on the one site outside the annotation mechanism. Its existing age gauge stays (it means "succeeded", not "ran").
- Meter names live in `ProductMetrics` (its header rule): `hamstrack.scheduled_job.last_run_timestamp_seconds`, `.period_seconds`, `.failures`. Per replica → rules use `max by (job)`.
### 5.2 Counters
- `ProductMetrics.mailDropped(MailDropReason)` → `hamstrack.mail.dead_letter_skipped{reason}`; `MailDropReason {BEST_EFFORT, POOL_CONTENDED, HOURLY_CAP, WRITE_FAILED, IN_FLIGHT_INTERRUPTED, FOREIGN_TASK}`; emitted at the seven branches in §2 row 4 (HD-234).

### 5.3 Alert rules (rules.yml, same group; `noDataState: OK` like the file, **except** `ScheduledJobStale`, which is `NoData → Alerting`: absence of the series *is* the finding, as `MailConcentrationGaugeStale` argues at AnonymousMailConcentration:102–105)
| Rule | expr (A) → threshold (B) | for | sev |
|---|---|---|---|
| `ScheduledJobStale` | `max by (job) ((time() - hamstrack_scheduled_job_last_run_timestamp_seconds) / (3 * hamstrack_scheduled_job_period_seconds + 900))` → `> 1` | 15m | warning |
| `ScheduledJobFailing` | `sum by (job) (increase(hamstrack_scheduled_job_failures_total[1h]))` → `> 0` | 0m | warning |
| `MailDeadLetterSkipped` | `sum(increase(hamstrack_mail_dead_letter_skipped_total{reason!="best_effort"}[1h]))` → `> 0` | 0m | warning |
Family relation: 3·period+15 min is the same "one missed run is silence, a stopped job pages within a few periods" bound rule 1 enforces on the timers; 900 s is the deploy allowance the mail-gauge rule already uses (1800 s over `for: 10m`, ProductMetrics:369–370). **Amended in the fix loop (ops-reviewer):** uncapped, that bound is ~72 h for a daily task, and the deploy cadence re-seeds `last_run` inside it, so the shipped rule is `min(3·period + 900, period + 4500)` — spelled `p + 900 + 2 * clamp_max(p, 1800)` because PromQL's `clamp_max` takes a scalar — giving hourly 2 h 15 min and daily 25 h 15 min, unchanged at or below a 30-minute period. `signup_refused` gets **no rule** (a knock on a closed door is information; the counter plus a `docs/observability.md` row is its witness).
### 5.4 Drill log (owner action, not builder)
New `### 4.1 Alert delivery drill log` under §4 of `docs/ops-prod-hardening.md`, table `| Date | Contact point | Triggered by | Received where / by whom | Delay | Notes |`, first column ISO date, second the contact point name in backticks. A drill = Grafana → Contact points → *Test* on `email`, **or** a real rule fired on purpose; the row records which. **Staleness: red at > 60 days, on age alone.** Reasoning: the thing that breaks delivery (the inbox behind `${OBS_ALERT_EMAIL_TO}`, SMTP credentials, Grafana's own health) lives outside the repo, so "red only when the contact point changed" is unmeasurable for exactly the failures it should catch (contactpoints.yml:15–17 mailed an undeliverable domain "for months" with the file unchanged). 60 days = two of the monthly checkpoints (`checkpoint.mjs`, from 2026-09-21), longer than any release cycle, shorter than the retro's silent windows. **The test is red until the owner writes the first row** — that is the `ops_witness` gate doing its job, not a defect in the test.
